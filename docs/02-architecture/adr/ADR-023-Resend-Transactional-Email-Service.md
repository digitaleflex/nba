# ADR-023 — Resend Transactional Email Service

> **Status:** Accepted
> **Date:** June 2026

---

# Context

NeverBrokeAgain relies heavily on transactional emails throughout the user lifecycle.

Examples include:

* Account verification
* Password reset
* Login security alerts
* KYC approval
* KYC rejection
* Broker verification approval
* Broker verification rejection
* Subscription updates
* Administrative notifications

The email service must provide high deliverability, low latency, excellent developer experience and seamless integration with the application architecture.

---

# Decision

The platform adopts **Resend** as the official transactional email provider.

Resend will be responsible for delivering all transactional emails generated by the application.

Emails are generated asynchronously through BullMQ workers.

The web application never sends emails directly during HTTP requests.

---

# Responsibilities

Resend is responsible for:

* Email delivery
* Email tracking
* Domain authentication
* Bounce handling
* Webhooks
* Delivery status

Business logic remains inside the application.

---

# Email Types

The platform supports the following transactional emails.

Authentication

* Verify Email
* Reset Password
* Password Changed
* New Device Login

Verification

* KYC Approved
* KYC Rejected
* Broker Verification Approved
* Broker Verification Rejected

Subscriptions

* Subscription Activated
* Subscription Updated
* Subscription Expired

Platform

* Welcome Email
* Security Notification
* Important Announcement

# Workflow

```text
Business Event

↓

Notification Service

↓

BullMQ Queue

↓

Background Worker

↓

React Email Template

↓

Resend API

↓

Recipient
```

# Reasons

Resend provides:

* Excellent Next.js integration
* Native React Email support
* TypeScript SDK
* High deliverability
* Domain verification
* Modern API
* Simple developer experience
* Reliable webhook support

It aligns perfectly with the NBA technology stack.

---

# Alternatives Considered

## SMTP

Rejected.

Reasons:

* Higher maintenance
* Lower reliability
* Limited monitoring

---

## Nodemailer

Rejected.

Reasons:

* Depends on external SMTP providers
* Less scalable
* More operational overhead

---

## SendGrid

Rejected.

Reasons:

* More complex API
* Higher pricing for expected usage
* Less modern developer experience

---

## Amazon SES

Rejected.

Reasons:

* Additional AWS infrastructure
* Longer setup
* Higher operational complexity

---

## Mailgun

Rejected.

Reasons:

* More configuration required
* Less integrated with React Email

---

# Consequences

## Positive

* Excellent developer experience
* High email deliverability
* Easy integration
* Low maintenance
* Scalable architecture
* Strong TypeScript support

---

## Negative

* External dependency
* Monthly costs increase with email volume

These drawbacks are considered acceptable.

---

# Architectural Rules

The application must never send emails directly from:

* React Components
* Server Actions
* Route Handlers
* Services

Every email must pass through the Notification Service and BullMQ.

Business services publish notification events only.

Workers are responsible for email delivery.

React Email is the standard solution for all email templates.

Email templates must remain presentation-only.

Business logic is prohibited inside templates.

---

# Failure Strategy

If Resend is temporarily unavailable:

* the BullMQ job must be retried automatically;
* failed jobs must be logged;
* permanent failures must trigger alerts;
* application workflows must continue whenever possible.

Email delivery failures must never rollback completed business transactions.

---

# Security Considerations

The platform must:

* authenticate the sending domain;
* use verified sender addresses;
* never expose API keys;
* store secrets as environment variables;
* validate webhook signatures.

---

# Future Evolution

The Notification Service must support additional providers if required.

Potential providers include:

* Amazon SES
* Mailgun
* SendGrid
* Postmark

The business layer must remain provider-independent.
